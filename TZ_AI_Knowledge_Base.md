# AI Knowledge Base / Personal Agency OS

Версия: 1.0
Дата: 06.08.2026
Статус: Черновик для старта разработки MVP

---

## 1. Общее описание проекта

### 1.1 Название
AI Knowledge Base (рабочее название ядра системы), часть более крупной системы **Personal Agency OS**.

### 1.2 Назначение
Персональная интеллектуальная система, которая автоматически превращает любой входящий контент (видео, статьи, заметки, идеи) в структурированную, связанную и доступную для поиска базу знаний, снимая с пользователя необходимость вручную обрабатывать и запоминать информацию.

### 1.3 Проблема, которую решает система
Ежедневно накапливается большой поток контента (Reels, TikTok, YouTube Shorts, статьи, идеи, технические решения), который сохраняется, но практически никогда не пересматривается. Через несколько месяцев информация фактически теряется — её невозможно найти и использовать.

### 1.4 Целевой пользователь на старте
Сам автор проекта — владелец агентства, потребляющий большой объём профессионального контента (AI, разработка, маркетинг, дизайн, продажи). В перспективе — коммерческий SaaS для разработчиков, предпринимателей и агентств.

## 2. Ключевой принцип: разделение на фазы

Главный риск проекта — избыточный scope. Ниже — намеренно жёсткое разделение по фазам. **Каждая фаза должна быть доведена до рабочего состояния до начала следующей.**

| Фаза | Содержание | Цель |
|---|---|---|
| **Фаза 1 — MVP** | Core loop: добавить контент → обработать → сохранить → найти | Проверить, что система реально используется ежедневно |
| **Фаза 2** | Personal Agency OS: проекты, задачи, ТЗ, привязка знаний к проектам | Расширение до полноценного рабочего инструмента |
| **Фаза 3** | Semantic search (vector DB), knowledge graph, автосвязи | Углубление интеллектуальности системы |
| **Фаза 4** | SaaS: мультипользовательность, биллинг, публичные интеграции | Коммерциализация |

Данное ТЗ фокусируется на **Фазе 1 (MVP)** с описанием архитектуры так, чтобы она не мешала последующим фазам, и на верхнеуровневом описании Фаз 2–4 для понимания направления роста.

## 3. Фаза 1 — MVP: Core Loop

### 3.1 Цель MVP
Пользователь может отправить материал (ссылку, файл, голосовое, текст) в систему одним действием и через некоторое время получить структурированную карточку знания, которую можно найти через поиск на естественном языке.

### 3.2 Пользовательский сценарий (happy path)

1. Пользователь пересылает ссылку/файл/голосовое сообщение в Telegram-бота.
2. Бот подтверждает приём и ставит материал в очередь на обработку.
3. Система определяет тип контента и запускает соответствующий пайплайн обработки.
4. Система выполняет AI-анализ и формирует карточку знания.
5. Бот присылает пользователю готовую карточку (резюме, теги, категория, оценка полезности).
6. Пользователь в любой момент может написать боту вопрос на естественном языке и получить релевантные материалы со ссылками на источники.

### 3.3 Входные источники (MVP)

Только источники, не требующие агрессивного скрейпинга соцсетей (см. Раздел 8, риск с ToS):

- Прямая пересылка видео/фото файлом в Telegram
- Ссылка на YouTube (через официальный API/yt-dlp для личного использования)
- Ссылка на статью (веб-страница)
- PDF-документ
- Голосовое сообщение
- Текстовая заметка / идея от пользователя

**Вне MVP:** прямой автоматический скрейпинг Instagram Reels / TikTok по ссылке — реализовать позже, отдельно оценив ToS-риски, либо через ручную выгрузку пользователем файла.

### 3.4 Обработка контента по типам

#### Видео (YouTube / загруженный файл)
1. Извлечение аудиодорожки
2. Транскрибация речи (Whisper API либо аналог)
3. Извлечение ключевых кадров (например, 1 кадр на N секунд или по смене сцены)
4. OCR текста на кадрах (если есть текст на экране)
5. Объединение речи + текста с экрана в единый текстовый контекст

**Оптимизация стоимости (важно):** двухступенчатая обработка.
- Шаг 1 (дешёвый): транскрибация + краткий анализ по первым ~20% контента → предварительная оценка релевантности.
- Шаг 2 (дорогой, полный): запускается только если предварительная оценка выше порога, либо по запросу пользователя (lazy processing).

#### Изображения
1. OCR всего текста на изображении
2. Определение визуального контекста (описание изображения через vision-модель)

#### Статьи / веб-страницы
1. Извлечение основного текста (readability-парсинг, без рекламы/навигации)
2. Определение структуры (заголовки, списки)
3. Извлечение основных мыслей

#### PDF
1. Извлечение текста (включая OCR для сканов)
2. Определение структуры документа

#### Голосовые сообщения
1. Транскрибация речи в текст

#### Текстовые заметки / идеи
1. Обработка напрямую, без дополнительного извлечения

### 3.5 AI-анализ (единый для всех типов после извлечения текста)

После получения полного текстового представления материала AI формирует:

- краткое описание материала (2–3 предложения)
- основную мысль (1 предложение)
- ключевые идеи (список)
- практические выводы / рекомендации к внедрению
- список упомянутых инструментов
- список упомянутых технологий
- список ссылок (если есть)
- автоматические теги (**из управляемого словаря**, см. 3.6)
- категория (**из фиксированного списка**, см. 3.6)
- оценка полезности (контекстная, см. 3.7)

Реализация: один структурированный промпт с JSON-выводом (schema-constrained output), чтобы гарантировать предсказуемый формат карточки.

### 3.6 Управляемая таксономия (решение недочёта "тег-хаос")

**Проблема источника:** свободная генерация тегов AI со временем создаёт несогласованный, разрастающийся словарь (`#cursor-ai`, `#cursor`, `#ai-coding` — по сути одно и то же).

**Решение для MVP:**
- Ведётся таблица `categories` — фиксированный, редактируемый пользователем список категорий верхнего уровня (AI, Маркетинг, Продажи, Программирование, Дизайн, Бизнес, Фриланс и т.д.).
- Ведётся таблица `tags` — управляемый словарь тегов.
- При анализе AI **сначала пытается выбрать** тег/категорию из существующего словаря (передаётся в промпт списком).
- Если подходящего тега нет — AI может предложить новый тег, но он попадает в статус `pending` и требует подтверждения пользователем (либо автоматически подтверждается, если пользователь включил "доверительный режим" — настройка на будущее).
- Раз в период (например, еженедельно) — простая проверка на дубликаты/похожие теги (можно вручную на MVP).

### 3.7 Оценка полезности (решение недочёта "субъективность оценки")

**Проблема источника:** абсолютная оценка ("2/10, вода") может неоправданно "похоронить" материал, ценность которого проявится позже в другом контексте.

**Решение для MVP:**
- Оценка полезности — **не скрывает** материал физически, а только влияет на сортировку/приоритет в выдаче.
- Оценка сопровождается коротким обоснованием (почему низкая/высокая), а не просто числом.
- Пользователь может вручную скорректировать оценку в любой момент.
- В карточке хранится дата оценки — в будущем (Фаза 2+) можно добавить пересчёт оценки в контексте активных проектов пользователя.

### 3.8 Хранение — структура записи базы знаний

Каждый материал сохраняется как запись со следующими полями:

```
id
title                — название
source_type          — тип источника (youtube, article, pdf, voice, note, image)
source_url           — оригинальная ссылка (если есть)
created_at           — дата добавления
raw_text             — извлечённый полный текст/транскрипт
summary              — краткое резюме
main_idea            — основная мысль
key_ideas[]          — ключевые идеи
practical_takeaways[]— практические выводы
tools[]               — упомянутые инструменты
technologies[]        — упомянутые технологии
links[]               — упомянутые ссылки
category              — категория (из словаря)
tags[]                — теги (из словаря)
usefulness_score      — оценка полезности (1-10)
usefulness_reason     — обоснование оценки
processing_status     — статус обработки (queued, processing, done, failed)
```

### 3.9 Поиск (MVP-версия)

Для MVP — без полноценной векторной базы данных (это Фаза 3), но с базовым RAG-подходом:

1. Пользователь задаёт вопрос на естественном языке боту.
2. Система выполняет поиск по ключевым словам/тегам/категориям + full-text search по `raw_text` и `summary` (например, PostgreSQL full-text search или简单 embedding-поиск через pgvector — допустимо внедрить сразу базовый вариант pgvector, если не усложняет MVP).
3. Найденные релевантные записи передаются в LLM вместе с вопросом пользователя для формирования связного ответа.
4. **Обязательно:** ответ всегда сопровождается списком источников (ссылки на карточки в базе) — во избежание галлюцинаций и невозможности проверить ответ (см. Раздел 8, риск 7).

### 3.10 Интерфейс MVP

- **Telegram-бот** — основной интерфейс приёма контента и поиска (минимальная точка входа, не требует отдельной разработки UI).
- **Простой веб-интерфейс (опционально для MVP, обязательно для Фазы 2)** — список карточек, фильтры по категориям/тегам, просмотр отдельной карточки.

### 3.11 Критерии готовности MVP (Definition of Done)

MVP считается завершённым, когда:

- [ ] Пользователь может отправить ссылку/файл/голосовое/текст в Telegram-бота
- [ ] Система автоматически определяет тип контента и запускает нужный пайплайн обработки
- [ ] Для каждого типа контента работает извлечение текста (транскрибация/OCR/парсинг)
- [ ] AI формирует структурированную карточку знания по единой схеме
- [ ] Карточка сохраняется в базе данных
- [ ] Теги и категории берутся из управляемого словаря
- [ ] Пользователь может задать вопрос на естественном языке и получить ответ со ссылками на источники
- [ ] Оценка полезности рассчитывается и отображается с обоснованием
- [ ] Система стабильно работает при ежедневном использовании в течение 2 недель тестового периода

## 4. Технический стек

**Бюджетное ограничение проекта: $0/мес.** Инфраструктура — собственный VPS (2 GB RAM, без GPU). Это исключает self-hosted транскрибацию и self-hosted LLM на самом VPS (нехватка RAM для стабильной работы Whisper/LLM одновременно с Postgres/Redis/FastAPI/ботом). Вместо этого используются бесплатные облачные inference-API с щедрым rate-limit.

| Компонент | Технология | Комментарий |
|---|---|---|
| Backend | Python + FastAPI | На VPS, лёгкий по ресурсам |
| База данных | PostgreSQL | На VPS; pgvector — не в MVP |
| Очередь задач | ARQ + Redis | На VPS |
| Транскрибация | **Groq API (Whisper large-v3)** | Бесплатный tier, работает без нагрузки на VPS |
| OCR | Tesseract | Self-hosted на VPS — лёгкий, не требует много RAM |
| AI-анализ | **Groq API (Llama 3.3) или Google AI Studio (Gemini free tier)** | Бесплатный tier вместо платного Claude API |
| Интерфейс приёма | Telegram Bot API | Бесплатно |
| Хранение файлов | Локальная файловая система VPS | Абстракция за интерфейсом, чтобы позже можно было перейти на S3 |
| Веб-интерфейс (опц.) | React / Next.js | Для Фазы 2 |

**Риски бесплатного стека (зафиксировать и отслеживать):**
- Rate-limits бесплатных API-провайдеров (Groq / Google AI Studio) могут ограничивать скорость обработки при пиковой нагрузке — для персонального ежедневного использования это не должно быть критично, но нужно обрабатывать `429`-ошибки с ретраями и очередью.
- Условия бесплatных tier'ов у провайдеров могут меняться — держать конфигурацию модели/провайдера в `.env`, чтобы можно было быстро переключиться на альтернативу (например, между Groq и Google AI Studio) без правки кода.
- Качество structured JSON-вывода у Llama/Gemini может быть менее стабильным, чем у Claude — обязательно предусмотреть валидацию схемы ответа и retry при невалидном JSON (см. Раздел 5, нефункциональные требования).
- 2 GB RAM VPS — минимален даже без LLM/Whisper; следить за потреблением памяти Postgres/Redis под нагрузкой, при необходимости — своп-файл как временная страховка.

## 5. Нефункциональные требования

- **Асинхронность обработки:** тяжёлые операции (видео, OCR) не должны блокировать бота — обработка через очередь задач с уведомлением пользователя по готовности.
- **Идемпотентность:** повторная отправка того же материала не должна создавать дубликат (проверка по хэшу контента/URL).
- **Отказоустойчивость:** если обработка упала — материал не теряется, статус помечается `failed`, есть возможность повторной обработки.
- **Стоимость:** проект работает на бесплатных tier'ах API (Groq / Google AI Studio) — тем не менее логирование использования (токены/минуты на материал) сохраняется, чтобы отслеживать приближение к лимитам бесплатного tier и вовремя переключаться между провайдерами.
- **Устойчивость к ошибкам бесплатных API:** обработка `429 Too Many Requests` через retry с backoff и постановку задачи обратно в очередь; валидация JSON-ответа AI-анализа по схеме с retry при невалидном выводе.
- **Приватность:** личные данные и контент пользователя не должны использоваться для обучения сторонних моделей (проверка условий используемых API).

## 6. Фаза 2 — Personal Agency OS (верхнеуровнево)

Активируется только после стабильной работы MVP.

- Управление проектами: идея → AI помогает оформить → создаётся проект → AI генерирует ТЗ → проект разбивается на задачи.
- Автоматическая привязка релевантных материалов из базы знаний к задачам/проектам.
- Управление клиентами.
- Полноценный веб-интерфейс вместо/в дополнение к Telegram-боту.

## 7. Фаза 3 — Semantic Search и Knowledge Graph (верхнеуровнево)

- Полноценная векторная база данных (Qdrant/Pinecone) для поиска по смыслу, а не по словам.
- Автоматическое построение связей между материалами — **начиная с простой модели** (связь через общие теги + векторную близость), без попытки сразу построить сложный граф произвольной глубины.
- Визуализация связей знаний.

## 8. Фаза 4 — SaaS (верхнеуровнево)

- Мультипользовательский режим, аутентификация, биллинг.
- Официальные интеграции с источниками контента (юридически проверенные, в отличие от MVP-скрейпинга).
- Публичный API.

## 9. Риски проекта и их митигация

| Риск | Митигация |
|---|---|
| Высокая стоимость обработки видео при масштабе | Двухступенчатая обработка (Раздел 3.4), lazy processing |
| Тег-хаос при свободной генерации AI | Управляемый словарь тегов/категорий (Раздел 3.6) |
| Некорректная "абсолютная" оценка полезности хоронит важный материал | Оценка не скрывает, а только сортирует; ручная корректировка (Раздел 3.7) |
| Knowledge graph — расплывчатая, сложная в реализации фича | Вынесена в отдельную Фазу 3, MVP без неё |
| Слишком широкий scope — риск незавершённого проекта | Жёсткое разделение по фазам (Раздел 2), MVP = только core loop |
| Скрейпинг Instagram/TikTok — риски ToS/бана | В MVP — только ручная пересылка файлов, без автоматического скрейпинга по ссылке |
| Галлюцинации при поиске | Ответ всегда сопровождается ссылками на исходные записи (Раздел 3.9) |
